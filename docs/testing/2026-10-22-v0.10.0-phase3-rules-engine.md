## Structure and public entry

`RulesEvaluator.evaluate(context: RuleEvaluationContext): RuleEvaluation` combines Focus/Deep and Daily/Session candidate facts, selects a winner, retains every lower-priority candidate and records exemptions, missing facts and unavailable prerequisites. It owns no counters, caches, clocks or transition state.

- `FocusCandidateEvaluator`: ordinary Focus delegates to existing `FocusEnforcementPolicy.shouldBlock`, with explicit supplied time and own-app classification. Deep reuses `FocusModeState.isDeepFocusActive(now)` and consumes the already-resolved TargetDisposition; it does not copy package/class heuristics from the Android essential-app resolver.
- `DailySessionCandidateEvaluator`: Daily delegates arithmetic/reached semantics to `UsageLimitEvaluator.evaluateSeconds`; Session reads the existing owner's snapshot.
- `RulePriorityResolver`: explicit weights 400 / 300 / 200 / 100 for Deep / Focus / Daily / Session. No ordinal sorting.
- `CandidateCapabilityEvaluator`: annotates each matched candidate's unmet prerequisites, including suppressed candidates.
- `RulesEvaluator`: composes these pure results. It does not choose an Android command or presentation.

The domain result distinguishes **matched business intent** from **ability to execute**. `selected != null` is not proof of protection, attachment or HOME success.

## Narrow Phase2 contract adjustments

1. `RuleFactGap(rule, fact)` replaces global missing-fact enums in RuleEvaluation. A Deep classification gap cannot be mistaken for a Daily accounting gap.
2. `CandidateCapabilityGap(candidate, capability)` replaces the global capability enum set. Requirements remain attributable to the exact selected or suppressed candidate. Only currently unavailable prerequisites are listed; they are not a second runtime state.
3. `DailyEdgeSnapshot` gains `displayRetryReady` and `observationAvailable`. Retry readiness is supplied, not scheduled here. `previousOverLimit = null` with an available observation remains the v0.9.0 first-observation false baseline; explicit unavailable edge facts are not treated as a crossing.
4. Ordinary `FocusRuntimeSnapshot.Focus` gains status so COMPLETED is expressible and cannot block. A `Concurrent` immutable snapshot can express independent Focus and Deep facts for the required all-four matrix. Legacy persisted Focus modes remain mutually exclusive; no adapter, new mode or runtime selection was implemented.

The corresponding RuleContractsTest and RuntimeSnapshotsTest were updated. Frozen collection ownership is retained; no conversion to unsafe collection-bearing data classes. Other Phase2 profile/context/execution files and fixtures are unchanged.

## Rule semantics

### Deep and Focus

Deep requires ACTIVE and the supplied start-inclusive/end-exclusive window. ORDINARY_APP yields a Deep candidate. Own app, launcher, input method, System UI, recognized necessary call UI, recovery settings and lockscreen yield a **Deep-only** exemption with the exact disposition as reason. Other rules continue and compete. UNCLASSIFIED yields `RuleFactGap(DEEP_FOCUS, TARGET_CLASSIFICATION)` without assuming ordinary or globally allowing all rules.

Ordinary Focus requires an active window, ACTIVE status, membership in the blocked set and a non-own target. Managed eligibility is intentionally not required. COMPLETED/expired Focus and Deep do not block.

The same-context matrix evaluates all 16 subsets of the four rules, including theoretical concurrent Focus/Deep input. Essential-target tests evaluate 7 essential dispositions against all 8 combinations of remaining Focus/Daily/Session facts, including own-app exclusion for ordinary Focus.

### Daily

Managed eligibility and an Explicit quota are required. Unset does not generate a quota or a missing-usage error. Unknown daily accounting differs from known zero use. Effective seconds are base seconds plus the supplied current-day extension; neither value is changed.

Enforcement parity intentionally retains **Explicit(0) + usage 0 = not reached**, while positive usage with zero quota is reached. This does not change the known Detail UI 0/0 display difference.

A Daily candidate requires reached usage and supplied crossing, entered-while-over or ready-retry facts. Reason precedence is crossing, entry, retry. Evaluation does not update previousOver, consume entry, mark notification receipts or grant extension. Repeating the same edge snapshot repeats the same result; consuming that event belongs to the transition/execution owner, not to a hidden evaluator cache.

### Session

Only the supplied episode threshold is used, not a recomputed profile default or physical-session elapsed value. No episode snapshot means known absence, as established in Phase2. A pending REMINDER/REENTRY gate suppresses new candidates even after its countdown expires; an elapsed but still-open decision is not an implicit dismissal.

For APP_ENTERED, a live bypass or already-admitted visit suppresses a new entry candidate without consuming the token. Otherwise an armed gate produces REENTRY_GATE_ELIGIBLE. On ordinary continued-use ticks, admission does not cancel the next EPISODE_THRESHOLD_REACHED reminder. Expiry is exclusive, matching the existing consumeBypass predicate. The engine does not clear expired tokens.

Only SessionFrictionManager remains the transition owner. The tests construct snapshots from its actual stage/gate outputs; the engine never advances 600 → 1080 → 1560 → 1860 itself. Its last-engagement field is not used to invent a new idle-reset timer. Usage-day identity changes retain the same episode, stage and admission snapshot.

## Compatibility findings, abstraction differences and Phase4 handoff

The tested pure rule predicates and stage snapshots match the 99 stated legacy helper cases. This is not an end-to-end runtime parity claim. The following distinctions are deliberate and must be reviewed at Checkpoint A:

1. Legacy Deep policy mixes Overlay availability with ALLOW/BLOCK execution disposition. The new layer retains matched business intent plus capability gaps. It cannot be used as a direct HOME/Overlay authorization. Deep-specific exemptions retain lower-rule facts, but real essential-UI handling remains an execution-layer obligation.
2. Concurrent Focus/Deep facts serve the required domain arbitration matrix; the existing persisted mode is exclusive. A legacy adapter should supply only its actual mode, not manufacture simultaneous activation.
3. Daily candidates here are **new intervention eligibility** based on supplied edge/entry/retry. Existing UsageMonitorService also suppresses Session while its current effective Daily limit is already reached, even on a stable over-limit tick without a new display edge. Consequently, selected Session in an isolated no-Daily-edge context must not be wired straight to display and bypass that existing guard. Phase4 must preserve this surrounding gate; current tests prove edge/helper parity, not replacement of the service's entire scheduling loop.
4. Window ownership, already-visible overlays, stale generations/revisions, real HOME/launcher confirmation, display retry timing, actual receipt commit and Focus completion presentation remain outside evaluation. No ExecutionPlanner or receipt handler was implemented.

Recommended first Phase4 slice, **only after owner / ChatGPT approval**: add a legacy snapshot adapter and shadow comparison in the existing monitoring path. Read actual mode/status/target classification, effective quota/edge and Friction snapshot without creating new transition owners. Preserve current over-limit suppression, occupied-window guards and receipt success semantics; initially compare only, never execute two paths. Do not switch both Services at once.

Known limitations: no Android adapter/execution validation, no device/vendor/permission lifecycle verification this phase, and no new Profile persistence or selection behavior. Host build success is not device acceptance. Phase4 has not begun; stop here for Checkpoint A review.

### B. Active constraints versus eligible display candidates

`RuleEvaluation.activeConstraints: Set<RuleKind>` is a frozen, per-evaluation result. It is computed from the current supplied facts, not a persisted flag or a mutable cache. The existing `selected` and `suppressed` candidates continue to represent intervention eligibility; no placeholder Daily candidate is created just to maintain priority.

Daily calculation still uses UsageLimitEvaluator and `base + todayExtension`. If Daily is reached, its constraint is active regardless of whether crossing, entry or retry allows a new display. An unavailable display edge produces a missing-edge fact while retaining a known reached constraint. Unknown usage is different: it produces a Daily usage gap, not a fabricated active constraint. Unset and explicit zero retain the existing meanings.

RulePriorityResolver now considers the strongest active constraint as well as candidate kinds. It selects an eligible candidate only at that priority. Session suppression uses the explicit `DAILY_ACTIVE` reason when Daily is dominant; higher Focus/Deep priorities remain unchanged. RulesEvaluator supplies the computed constraints to the resolver. There is no additional Daily arbitration helper left for Service to invent.

| Current facts | Active Daily | Selected actionable candidate | Suppressed Session |
| --- | --- | --- | --- |
| Below effective quota, Session due | NO | SESSION | NO |
| Reached, crossing/entry/retry eligible, Session due | YES | DAILY | DAILY_ACTIVE |
| Reached, no crossing/entry/retry, Session due | YES | None | DAILY_ACTIVE |
| Supplied +900 extension makes quota greater than use | NO | SESSION, if due | NO |

Thus `selected == null` does not imply that every rule is inactive. A stable over-limit evaluation can carry active DAILY plus a suppressed Session without any new Daily display action. Evaluation never invents retry, advances a stage, consumes a gate/token or writes an extension. Usage-day/config changes are evaluated from the newly supplied facts without resetting the Session snapshot.

### Legacy continuous-suppression parity

The source of the old surrounding behavior is **UsageMonitorService.processForegroundApp**, specifically the `selectInterventionType` call at lines 335–341:

```kotlin
dailyLimitTriggered = dailyTriggered || (evaluation?.isLimitReached == true && dailyAvailable)
```

`selectInterventionType` at lines 910–918 returns DAILY_LIMIT_REACHED before Session. Actual Daily display was separately handled earlier by `handleInterventionDecision(decision)`. `LimitInterventionManager.evaluate` at lines 69–75 requires reached use, an unoccupied display and crossing / entry / ready retry. Therefore the selector's DAILY result on a stable over-limit tick was a suppression marker, not a request for another overlay.

DailyContinuousSuppressionParityTest adds **13 individually reported cases**. It feeds existing UsageLimitEvaluator / LimitInterventionTriggerState / selectInterventionType helpers and compares both:

- continuous reached-state suppression;
- actual eligible intervention, distinguishing a new Daily display from suppression-only Daily state.

The parity group covers below, exact/above crossing, stable exact/above, over-entry, ready retry, supplied extension release, extended boundary, new usage day, zero-quota zero/positive use, and stable over-limit without a due Session. Permissions and window availability are held available to isolate this business rule; this does not claim Android presentation parity.

**Future wiring no longer needs an extra Daily-over-Session business guard.** It must still preserve execution availability, window ownership and success receipts, which are not duplicate business arbitration. The old Service guard remains physically unchanged because this task forbids runtime wiring; Phase4 will consume the hardened domain result instead of reproducing that guard.
