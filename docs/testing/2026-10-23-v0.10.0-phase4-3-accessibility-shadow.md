## Adapter and classification

New code lives under `app/src/main/java/com/example/timemanager/accessibility/rules/`:

- `AccessibilityRulesSnapshotAdapter`: immutable legacy Focus, configuration, Daily and Episode facts → RuleEvaluationContext. No clock, Android command or business-state mutation in the adapter.
- `AccessibilityTargetClassifier`: maps identities from the existing DeepFocusEssentialAppResolver plus the existing necessary-call/recovery predicates into TargetDisposition.
- `AccessibilityRulesCompatibilityProjection`: maps the RulesEvaluator winner and capability/window facts into the legacy action vocabulary; no second priority ranking.
- `AccessibilityRulesShadow`: six-state comparison, exception isolation, identity checks and deduplicated diagnostic sink.
- `AccessibilityRulesObserver`: Debug-only Service wiring, lifecycle-bound read-only configuration Flow mirror and observation hooks. The observer is never constructed in Release.

Classification covers own app, launcher, IME, SystemUI, recognized call/emergency UI, recovery settings, lockscreen, ordinary app and unclassified targets. Actual persisted FocusModeState is projected to Off, Focus or DeepFocus only. No artificial Concurrent runtime is created. COMPLETED, before-start and exact-end predicates remain inactive regardless of an informational completion overlay.

## Two observation points

### Focus / Deep window observation

Existing event filtering and stable-foreground handling run unchanged. The ordinary Focus path observes the same saved state and permission facts. Deep observation uses the disposition actually returned by the unchanged legacy Deep policy and the same application-overlay grant sampled for that call.

Window observations compare higher-rule business intent, not Overlay attachment, HOME acknowledgement, debounce or cleanup. Lower-rule facts are retained in the evaluation. A cached Daily value in a window observation is **not** declared a fresh re-entry check and is not used as fresh entry evidence.

### Session entry observation

```text
actual Coordinator entry/generation
→ capture read-only probe
→ ONE existing coordinator.checkEntry(entry)
→ Monitor's unchanged fresh Daily refresh / existing execution
→ compare observation before Accessibility token consumption
→ original Accessibility when(result) branch
```

No second CheckEntry, quota query/evaluator execution, HOME or gate request is issued by shadow.

Coordinator adds publication metadata (entry identity and increasing sequence) beside the existing Daily map, and exposes read-only managed/publication accessors. It does not introduce a second Daily calculation or owner. A Daily publication counts as fresh only when package/generation, usage day and later publication sequence match the probe. Cached, wrong-day or wrong-generation publications do not qualify. The original CheckEntry still owns the fresh refresh; metadata is evidence about that existing path, not a replacement refresh.

Canonical base/first-reminder seconds are mirrored from the existing repository Flows; no configuration writes occur. Policy revision advances on observed config/Focus changes. Missing configuration or incoherent base/effective facts are reported rather than synthesized. The adapter obtains extension as the difference between the existing effective limit and the observed configured base; negative/incoherent results are insufficient, not invented extension data.

For CHECK_FRICTION, the existing Episode is re-read after the fresh Daily check and before admission consumption, and elapsed time is re-sampled for token expiry. The read cannot consume a token, arm a gate or commit a stage. A stale generation/revision always yields STALE, including when legacy Daily execution has already sent HOME.

## Priority, capability and compatibility

RulesEvaluator / RulePriorityResolver retain the single domain ordering: **Deep > Focus > Daily > Session**. The projection maps its selected candidate/active constraint; it does not rank candidates independently. Debug legacy comparisons are observations of the old path, not an alternative execution authority.

- Ordinary Focus is independent of managed membership and application-overlay permission. Actual Accessibility connection remains required.
- Deep ordinary targets match even with missing application overlay, but the projection reports FAIL_OPEN / capability gap, not successful protection.
- Deep necessary-target exemption is scoped to Deep. Daily active constraints and Session candidates remain available in the same context; there is no engine-level global ALLOW.
- Daily suppresses Session at a fresh re-entry. An extension changing effective quota releases that constraint without resetting Episode.
- A live bypass or an admitted visit suppresses the re-entry candidate; evaluation does not consume either. An expired token does not suppress the candidate and is not cleared by evaluation.
- Pending gates are not recreated. A normal overdue Episode threshold is still Monitor-owned, not converted into a re-entry gate by this projection.
- Overlay ownership/availability remains execution metadata. No automatic preemption is added.

## Expected execution differences / review boundaries

These are explicitly named, not treated as unexplained business mismatches:

1. **Legacy Deep branch short-circuits lower execution.** On an exempt target the engine retains Daily/Session facts, while the legacy Service's active-Deep branch returns before invoking lower execution. Shadow does not fix this. 4.3B must review the corresponding Coordinator/fresh-entry handoff before authority can be switched safely.
2. **Legacy overlay suspension precedes Deep exemption classification.** An already-exempt target with missing application-overlay permission can suspend the old overlay even though no Deep constraint matches that target. This is presentation/capability behavior, not global permission to ignore lower rules.
3. **Normal threshold vs re-entry gate.** An overdue normal threshold with no armed re-entry stage remains Monitor execution, not a new Accessibility gate.
4. **Legacy request vs capability-gated execution.** The old entry path can request a gate that the existing Monitor capability checks then reject fail-open. The engine exposes the capability gap earlier; neither path claims protection or mutates the episode merely by evaluating.
5. **Daily already executed.** If identity is still current, comparison records that the legacy Monitor has already handled Daily and issues no second action. If HOME or another transition changed generation, the observation is STALE, never reused as actionable current entry.

4.3B's pre-execution decision/fallback placement is intentionally not implemented. This post-legacy-execution shadow handoff must not simply be reused to drive another command. Runtime shadow logs have not been collected in this host-only task.

## Phase4.3B Authoritative Switch — Host Implementation

Date: 2026-10-24. Branch: `feat/rules-engine`. Owner authorized host implementation only. The preceding 4.3A evidence is historical and unchanged; it does **not** establish device acceptance of the new authoritative path.

### Pre-execution authority and the one execution path

`TimeManagerAccessibilityService` now captures immutable target/identity/configuration facts and invokes `AccessibilityRulesAuthority.decide()` **before** intervention effects. The authority adapts facts, calls `RulesEvaluator`, and projects its resolved winner through `AccessibilityRulesCompatibilityProjection.authoritative()`. Ranking still comes exclusively from `RulePriorityResolver`; the compatibility projection maps, not ranks.

Window scope can execute Focus/Deep only. A Deep-exempt window may retain lower constraints in its evaluation, but its projection cannot manufacture a Daily or Session action from cached Monitor data. Only a real managed entry continues to the lower-rule path.

The entry sequence is:

```text
actual entry + generation + policy revision
  -> Coordinator.prepareEntryFacts
  -> Monitor PrepareEntry under existing timing mutex
  -> ONE existing refreshDailySnapshot, explicitly labelled with that entry
  -> immutable PreparedAccessibilityEntry
  -> adapter / RulesEvaluator / execution projection
  -> pre-effect identity check
  -> Monitor ExecuteEntry, identity recheck and one-generation claim
  -> ONE existing Daily / Session / admission / fail-open execution
```

Preparation reads the existing Daily accounting/effective-limit owner. It does not call the old `checkEntry()`, choose Daily-versus-Session, request HOME, show a window, consume a token, admit a visit, begin a Gate or advance a stage. Normal execution does **not** issue `CheckEntry` or `ShowReentryGate`; those old commands remain reachable only from the explicit legacy emergency fallback path. The new `ExecuteEntry` uses the prepared usage/base/effective values and never refreshes Daily a second time. The numeric `UsageLimitEvaluator` call in Daily execution constructs the existing owner's execution input from those same values; it is not a second accounting read.

The existing SharedFlow/coordinator relationship remains process-scoped and does not introduce Service-to-Service references. Monitor normal Daily/Session arbitration is unchanged.

### Identity, stale work and deduplication

- The rule identity contains package, foreground generation, usage-day key, policy revision and evaluation sequence. The entry ticket additionally contains the exact Daily publication sequence and entry.
- The service requires a new publication after preparation began, for that exact entry/day, and checks prepared base quota against the current configuration mirror.
- The runtime checks revision/day/generation before dispatch. Monitor checks the exact publication and claims the entry immediately before execution, after metadata loading. A repeated command for the same generation cannot execute twice.
- Wrong day, generation, revision or replaced publication is discarded, never routed through legacy with stale facts. Discard releases only the pending-preparation timing hold; it does not admit the visit or touch Episode/Gate/token/stage state.
- After an intentional HOME transition, existing launcher confirmation remains authoritative. Session continuation rechecks policy/day before beginning its Gate; Daily continuation rechecks policy/day before showing its window. Neither HOME API acknowledgement nor Engine selection substitutes for an observed launcher.

### Focus, Deep and lower-rule handoff

- Ordinary Focus uses Engine selection, existing action debounce and `TYPE_ACCESSIBILITY_OVERLAY`; application Overlay permission remains unnecessary.
- Deep ordinary targets use Engine selection and existing HOME/presentation execution. Missing application Overlay produces **selected Deep + missing capability + fail-open**, not business Allow or legacy fallback.
- Target resolution still uses `AccessibilityTargetClassifier` and the existing resolver/predicates. Unclassified remains explicit and produces a missing-classification fallback, not an essential exemption.
- Deep exemption is scoped to Deep. A real exempt managed entry can select Daily or Session using fresh facts; a generic exempt window cannot execute either from a cache.
- Coordinator keeps the current Engine higher-rule selection as an execution receipt tied to target and Focus state. This prevents its existing lower-action guards from reintroducing the old global Deep veto during the launcher handoff. Receipts are cleared on Focus changes/disconnect; they do not own Focus persistence, evaluate priorities or change Episode state.
- Overlay suspension/resumption remains presentation housekeeping. Existing lock/call/recovery predicates and `shouldResumeOverlayAfterSuspension` are reused. Missing Overlay on an exempt own/launcher target may still suspend an old window; this is not reported as Deep selection.
- Completed Deep still does not block ordinary apps; its existing completion presentation remains separate.
- Overdue normal Session thresholds without an armed re-entry stage remain Monitor-owned. The selected re-entry intent alone neither consumes a stage nor proves HOME success.

### Fallback and reverse shadow

`AccessibilityAuthorityDispatch` selects **Engine OR legacy fallback**, before calling either sink. Adapter/evaluator exceptions or genuinely missing critical facts can select fallback; normal capability denial cannot. An execution exception propagates to the existing fail-open handling and never invokes legacy afterward. A reverse-shadow disagreement cannot select fallback.

The emergency window fallback retains the old Focus/Deep flow. A prepared-entry fallback uses hypothetical legacy intent with the **same already-prepared facts**, rather than calling `checkEntry()` and reading Daily again. Unavailable preparation follows the old unavailable/fail-open outcome without a cached Daily decision.

Debug comparison now consumes the **actual authoritative plan** versus pure hypothetical legacy intent, pre-execution; it does not evaluate a second authoritative result or observe an already-consumed legacy decision.
