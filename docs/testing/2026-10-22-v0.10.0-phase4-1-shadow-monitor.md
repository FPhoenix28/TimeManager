## Adapter boundary and snapshot sources

New code lives in `app/src/main/java/com/example/timemanager/monitor/shadow/`:

- `LegacyRulesSnapshotAdapter.kt`: immutable legacy input → scoped RuleEvaluationContext. No repository calls or mutable state.
- `ShadowRuleComparison.kt`: typed, pure business/availability comparison.
- `MonitorRulesShadow.kt`: capture/evaluate/complete facade accepting only read callbacks and a diagnostic sink. It holds only shadow revision, observation sequence and diagnostic deduplication; no usage ledger, episode, stage, edge tracker, extension cache, capability cache or Focus state.

The adapter uses fixed `ProfileId.DEFAULT` only as legacy policy provenance. It creates no Profile store, migration, active-profile selection or UI. Missing Daily remains Unset; Explicit(0) stays explicit. Stored Session values remain explicit, including a value equal to the default. The episode's supplied next threshold remains authoritative even when profile configuration differs.

All three configuration streams must have emitted before shadow policy evaluation. The extra Session readiness flag is diagnostic only: it does not change the legacy startup or settings behavior. Missing config yields INSUFFICIENT_SHADOW_FACTS, not a fabricated empty policy. Unknown use, unavailable edge and inconsistent policy inputs are similarly classified instead of being called a business mismatch.

Daily notification receipts are not sampled by this intervention-only adapter. Their unused domain field remains a non-authoritative default; the shadow path neither compares nor writes notification receipts. Existing notifier behavior remains independent.

## Read-only owner additions

`LimitInterventionManager.readRulesSnapshot` reads the owner's maps under the Monitor's existing timing mutex. It exposes previous state, pending entry, retry readiness, display eligibility ignoring window occupancy, and the existing private display-occupied flag. The readiness predicate mirrors the existing manager condition using the supplied already-calculated reached fact. It neither calls evaluate nor consumes an entry, writes previous-over, schedules retry, queries repositories or changes extension.

`LimitInterventionTriggerState.readSnapshot` reads existing state only. Repeated reads leave a pending entry available for the next real evaluate call. Peeking a different usage day does not reset the old day's owner state. Existing evaluate/trigger/extension bodies are unchanged.

`InterventionCoordinator.foregroundObservation` is a synchronized four-line addition exposing the current foreground package with its existing generation. It does not establish/allow a visit, emit events, consume admission or advance generation. No AccessibilityService wiring changed.

## Identity and consistency

`MonitorRulesShadow.onPolicyChanged` increments a service-local **shadow identity counter** when the existing tracked, limit or stored-session Flow emits. Updates run inside the existing timing mutex. This is not a new atomic revision for the distributed legacy stores, is not persisted, and does not reset usage, episode, stage or ledger identity. Initial emissions may each advance it.

If Coordinator has a matching foreground observation, its generation is copied exactly and marked COORDINATOR. When no corresponding Coordinator observation exists, such as polling without connected Accessibility, `generationSource = MONITOR_OBSERVATION`; the domain generation slot uses constant zero, and the increasing evaluationSequence identifies the Monitor observation. It is explicitly **not** a second Coordinator generation system or proof of an app-entry event.

If Coordinator currently observes a different target, or the episode changed between the earlier legacy snapshot and shadow capture, the sample is insufficient rather than a fabricated mismatch. If a captured revision is no longer current at comparison, the result is STALE. These diagnostics do not alter actual monitoring. Cross-owner snapshots are not claimed to be globally atomic.

## Shadow insertion point and legacy order

In `UsageMonitorService.processForegroundApp`:

1. Existing timing and usage calculation run in their original order.
2. Immediately after the existing effective-limit/UsageLimitEvaluator calculation, Debug captures read-only inputs and evaluates the new engine. This is **before the current Daily/Session HOME/Overlay interventions**. Existing independent SessionTracker notification timing is not moved; the shadow does not take over notifications.
3. The existing publishDaily, daily notifier, ongoing notification, LimitInterventionManager.evaluate and handleInterventionDecision run unchanged.
4. The existing selectInterventionType still receives the same expressions, in the same order. Two `.also` assignments copy its actual Session-eligibility and occupied-window arguments into diagnostic locals. No expression is evaluated twice or replaced with an engine result.
5. Comparison receives the actual Daily decision, actual old selector result and those exact gate arguments before the old Session action. Its return value is ignored by the execution path.

The Monitor diff is **40 added / 4 removed lines**, including imports, configuration hooks and formatting of the existing settings assignment. The old Daily evaluate/selector is not called a second time. Early timing-pause and other return paths remain intact; shadow does not force evaluation while an overlay pauses the loop.

## Business parity versus execution availability

`ShadowRuleComparison.status` is one of MATCH, MISMATCH, INSUFFICIENT_SHADOW_FACTS, STALE or ERROR. A separate `executionDeferredBy` set expresses capability, coordinator gate, occupied window, occupied Daily display and a legacy gate changing after capture. Thus **business MATCH + execution deferral** represents an expected abstraction difference without mislabelling it a rule mismatch.

The comparison independently checks:

- Existing reached calculation versus active DAILY constraint.
- Read-only owner display eligibility versus an eligible Daily candidate, including suppressed candidates.
- Existing cached isReminderDue result versus the Session candidate fact.
- Business arbitration: display-eligible Daily wins; stable reached without display suppresses Session with no action; below quota allows due Session.
- Actual legacy manager Show/None result when Daily evaluation was allowed, with its private occupied-display flag respected.
- Actual legacy selector result versus its actual capability/window-gated inputs. No post-action permission re-read is substituted for the original selector arguments.

`ShadowDifference` identifies the differing field rather than logging an unstructured "different". Adapter/config/observation gaps are explicitly insufficient. No mismatches found here required modifying either Checkpoint A semantics or the legacy business path.

## Known expected differences and limitations

1. The old selector can return DAILY_LIMIT_REACHED solely to suppress Session. With stable over-limit state, the engine has active DAILY, no selected display action and suppressed Session. This is a business MATCH, not a missing Daily overlay.
2. Occupied windows or denied capability can defer actual display while the business candidate remains valid. These are typed execution deferrals, not false business mismatches.
3. Only Monitor Daily/Session is compared. Context Focus=Off is a **scope projection**, not an assertion about the actual Focus runtime. Non-own targets remain UNCLASSIFIED; no ordinary-app classification, Focus/Deep result or Accessibility re-entry result is invented. Actual coordinator gates remain part of execution availability. Full Focus/Deep/re-entry adapters belong to a later slice.
4. A physical-session start is evaluated as a Monitor TICK, not fabricated as APP_ENTERED. Episode continuity and gate/token lifecycle remain with existing owners.
5. The host tests do not prove live vendor behavior, actual HOME/Overlay presentation, asynchronous window effects or real-device parity. No device samples were collected. Release gating was statically inspected; no new Release build was requested or run.

## Exception isolation and diagnostics

Capture/evaluation and comparison exceptions become ERROR inside MonitorRulesShadow. A failing diagnostic sink is also contained. No shadow status can enter the monitor's existing failure cleanup or request failOpen/reset, stop monitoring, show/dismiss a page, HOME, grant extension or modify an episode.

Only abnormal diagnostic transitions are logged, with deduplication. MATCH is silent. Logs include category, differing fields, missing facts, revision/sequence and generation source, not Todo content, histories, app names or installed-app lists. The service invokes capture/config hooks only under BuildConfig.DEBUG; Release never instantiates/runs the shadow observer or emits its diagnostics.
