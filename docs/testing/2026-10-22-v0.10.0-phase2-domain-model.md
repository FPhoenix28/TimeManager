## Design choices

### Configuration provenance and runtime identity

- `DailyRuleConfig.Unset`不转为任何默认额度；`Explicit(0)`和`Explicit(1800)`保留不同值。没有将extension放入Daily配置。
- `FirstSessionReminder.InheritedDefault`解析为600秒，但类型仍不同于`Explicit(600)`；显式900/1200秒原样保留。
- `SessionProgression.thresholdSeconds(first, number)`是无副作用的一次性计算，首轮first，后续480、480、300、300…；不接收或推进可变Episode。
- 当天账本identity只有package+usageDayKey，没有ProfileId。Session snapshot也没有ProfileId或usageDayKey，可以表达跨Profile/04:00继续的同一Episode。新模型不会自行清账、重arm或切换Profile。
- Profile没有Focus活动状态或旧blocked集合导入逻辑。普通Focus选择集合独立于managed标记。
- Default ID固定为`default`；configVersion只声明配置格式，policyRevision/foregroundGeneration分别是评价事实的版本，不混用。

### Immutable facts and existing pure types

Snapshot全部通过val和不可变嵌套值表达。Profile的AppPolicy集合、Focus blocked set、RuleEvaluation的集合都经Kotlin buildList/buildSet复制并冻结；调用方之后修改输入集合不会改变快照。集合承载对象采用普通只读class，不开放可绕过复制的data-class copy入口。

复用现有纯类型`AccessibilityRuntimeState`、`FocusModeStatus`和`SessionGatePhase`；这些来源文件无Android依赖。没有新建语义重复的Accessibility三态。新domain无android/androidx/kotlinx、Repository/Room/DataStore/Service/Compose依赖，无系统时钟调用，无var或mutable runtime cache。

构造检查只覆盖基本语义：负usage/extension、非正阈值、无效时间窗、重复package配置和上下文跨包/跨日混装。没有实现权限检测、包名OS查询或04:00计算。

### Rule facts versus execution

`RuleEvaluationContext`只带target/time/effective configuration/Daily/Session/Focus/capabilities/event/identity。`ExecutionContextSnapshot`独立带overlay owner/attached、HOME可用、当前执行方式、pending decision和deadline。窗口占用不会把Daily事实改成未超额。

`TargetFacts`缺省为UNCLASSIFIED，不把未知包直接当普通目标；可表达own、launcher、IME/SystemUI、必要call/recovery/lockscreen事实。必要目标的allow是带rule scope的`RuleExemption`，不会抹掉其它候选事实。当前Daily数据不可用用null表示，区别于零用量；Session null明确表示尚无Episode。各输入的真实观测/新鲜度由未来adapter提供。

`RuleCandidate`为sealed typed variants，各自有明确reason/facts；`RuleEvaluation`可以同时保留selected Daily与suppressed Session，也可表达exemption、insufficient facts和required capability。枚举声明顺序没有被用于任何排序算法；selection在测试中显式构造，留待Phase3。

`EvaluationIdentity`包括package、foreground generation、policy revision、usageDay及调用方提供的evaluation sequence；没有生成计数器或stale拒绝算法。ExecutionProposal不代表成功。ExecutionReceipt区分SUCCEEDED/FAILED/STALE，成功还区分ALLOWED与OVERLAY_ATTACHED。HOME_UNCONFIRMED、OVERLAY_ATTACH_FAILED等保留为typed failure reason。

“Session due但attach失败”可表达为Session candidate+Failed receipt；所有输入快照仍是原值。本阶段没有receipt handler或状态推进方法。未来owner必须校验identity及真实effect后，才可让现有Friction owner提交stage，不能仅因评价为due或HOME API返回成功就提交。

## Limits and Phase 3 handoff

- 本轮证明类型和纯兼容计算可编译、可构造并满足focused断言，不证明真正Rules Engine已生效。
- 没有Profile选择/Default fallback算法，没有rule predicate/priority resolver，没有execution planner/receipt处理或generation stale rejection。
- 只读快照不会自动从当前Friction/Focus/Usage repositories生成；实际接线、加载状态/新鲜度以及HOME/attach的receipt来源在Phase4处理。
- Profile存储schema/migration、活动Focus恢复、Profile UI与Schedule不在此阶段；Statistics维持全局managed历史口径，没有新增归因字段。
